# Workflow

How we work in this repo.

## Setup

```bash
uv venv --python 3.12 && uv pip install -e .     # laptop
bash hpc/setup.sh                                # cluster, see hpc/README.md
```

## Repo layout

| path | what |
|---|---|
| `src/trailercut/` | one module per pipeline step, each runnable with `python -m trailercut.<step>` |
| `scripts/run_all.sh` | menu of rebuild stages; runs only the ones named (`data prep align audio rq1 viz`, opt-in `rq2` and `ebm`); no arguments lists them |
| `scripts/curate.sh` | steps that change the inputs: dead links, trailer audit and swaps, label page, tuning against the labels |
| `hpc/` | Slurm jobs for the heavy steps |
| `data/ids/` | film lists, trailer availability, recovery, audit and swap logs |
| `data/features/` | everything the analysis and views read |
| `labels/` | labeling tool, sample, gold labels |
| `figures/` | generated figures |
| `viz/` | D3 views (`index.html` = Trailer View, `rq1.html` = what gets picked across all films); `viz/data/` is generated by `viewer_export` and `rq1_export` and gitignored |
| `docs/` | these docs |

## Adding a pipeline step

1. New module `src/trailercut/<step>.py` with a top docstring: what it does, outputs, CLI usage.
2. Skip work that's already done, so reruns are cheap. A step that runs long (downloads, per-film
   checks) saves its log after every item and resumes past finished ones on rerun, so an interrupt
   loses at most the item in progress. Backups it makes must not be overwritten by a resumed run.
3. Paths from `trailercut.paths` only; never hardcode `data/`.
4. Add it to the right stage of `scripts/run_all.sh` (or to `scripts/curate.sh` if it changes the
   inputs: trailer links, labels), `docs/pipeline.md` and the README pipeline table.
5. New output files go in `docs/data_dictionary.md`, and either the committed list in the README or
   `.gitignore`.

## Rebuild vs curate

- `bash scripts/run_all.sh <stages>` (e.g. `bash scripts/run_all.sh rq1 viz`) only recomputes from the
  current inputs; with no stages it just lists them. Run it after code changes; name the stages from the one you touched onward.
- `bash scripts/curate.sh <step>` changes the inputs (which trailer a film uses, the labels). Run it on
  purpose, commit the changed logs in `data/ids/`, then rebuild with
  `bash scripts/run_all.sh prep align audio rq1 viz` (plus `rq2` and `ebm` when needed).
- YouTube steps (`recover`, `audit`, `swap-*`) are rate-limited: run swaps as `swap-search`,
  `swap-download` (resumable; rerun later if it stops on bot checks), `swap-apply` (resumable;
  `--batch` for hundreds of films). Add `--set expand` for films new to the dataset.
- Swapping a hand-labeled film's trailer drops its labels (`labels/label_trailers.csv`); when labeling
  a new film, add its `imdb_id` and current `youtube_id` there.

## What gets committed

Commit: code, IDs and logs, feature tables under ~20 MB, JSON reports, figures, gold labels.
Don't commit: videos, keyframes, embeddings, audio, anything that rebuilds in a few minutes and is
over ~50 MB. Check `git status` for large files before committing (`du -h` on anything new).

## Commits

- Small commits, one idea each, present tense ("Add ...", "Stop tracking ...").
- Pipeline outputs get their own commit ("Run pipeline on ..."), separate from code changes.

## Docs

- Every code change gets a docs pass: `design.md` for new decisions and why, `pipeline.md` and
  `data_dictionary.md` for new steps or files, `results.md` for new numbers, `experiments.md` for
  things tried, `TODO.md` for status.
- Numbers in docs come from committed outputs, never from memory.
- No dashes for ranges, write "0.78 to 0.93".
